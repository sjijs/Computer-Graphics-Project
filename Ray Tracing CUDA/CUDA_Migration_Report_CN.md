# CUDA迁移升级调研报告（路径追踪渲染器）

## 1. 报告目的
本报告面向当前项目的路径追踪渲染器，给出从 CPU 实现迁移到 CUDA 加速的可执行升级方案。目标是从“CPU 多线程离线/准实时渲染”升级到“GPU 交互式渐进渲染”，并为后续实时化能力（降噪、动态相机、复杂场景）奠定架构基础。

评审日期：2026-03-21

## 2. 当前项目状态概览
### 2.1 已具备能力
1. 路径追踪核心链路完整：`camera::render -> ray_color -> world.hit(BVH) -> material.scatter`。
2. 具备 CPU 侧基础优化：BVH、分块渲染、线程并行、渐进累积显示。
3. 场景与材质覆盖较全面：球体、四边形、三角网格、体积介质、贴图与噪声纹理。
4. 已支持窗口输出与相机运动，为交互式预览提供了基础框架。

### 2.2 典型负载规模
1. 模型面数（OBJ）：
   - `bunny.obj`: 10,000 faces
   - `armadillo.obj`: 30,000 faces
   - `chair.obj`: 50,704 faces
2. 贴图体量：存在多张 8K 级纹理（单张约 3MB~15MB）。
3. 场景参数中常见高采样/高反弹设置（如 500~1000 spp，max depth 50~200），当前更偏离线画质优先。

## 3. 关键问题与迁移阻塞点
### 3.1 架构阻塞（高优先级）
1. 大量运行时多态（`virtual`）+ `shared_ptr` + 对象图结构，不适合直接在 CUDA kernel 中高效执行。
2. 路径追踪和 BVH 遍历使用递归，GPU 上栈开销高、可控性差，不利于吞吐。
3. `double` 为核心数值类型，消费级 GPU 上 FP64 性能低，难以支撑实时目标。

### 3.2 并发与稳定性问题（高优先级）
1. 全局随机数接口与多线程并行有并发风险，且线程私有 RNG 未贯通到采样调用链。
2. 渲染流程默认持续循环，`render(world, filename)` 忽略文件输出，不利于基准测试与自动回归。

### 3.3 性能热点问题（中高优先级）
1. 体积介质变密度采样存在命中路径上的动态分配，不适合高吞吐执行。
2. 纹理访问与材质分支依赖对象间跳转，缓存局部性较弱，GPU 迁移后潜在分歧较高。

### 3.4 工程化问题（中优先级）
1. 当前构建链路未完成 CUDA 工程化（缺少 CMake CUDA 目标/`.cu` 编译流程）。
2. 任务脚本存在路径不一致与优化级别不足问题，影响后续迁移验证效率。

## 4. 迁移目标定义
### 4.1 总体目标
1. 建立 CPU/GPU 双后端：CPU 用于对照与回归，GPU 负责交互式渲染。
2. GPU 后端支持渐进式 1 spp/帧累计，优先实现“可交互预览”而非一步到位离线画质。
3. 支持后续扩展：降噪、动态场景、材质扩展、体积近似。

### 4.2 阶段性性能目标（建议验收）
1. 里程碑 M1：`800x450 @ 1 spp`，静态场景可交互渐进显示。
2. 里程碑 M2：`1280x720 @ 1 spp + 降噪`，常见场景达到流畅预览。
3. 里程碑 M3：中等复杂模型场景保持稳定帧间收敛，交互操作无明显卡顿。

## 5. CUDA迁移技术路线
## 5.1 路线原则
1. 先“数据结构与执行模型重构”，再“CUDA 并行化”。
2. 先“最小可用 GPU 路径追踪器”，再“实时化与质量优化”。
3. 全程保持 CPU 基线可运行，用于正确性与性能对照。

### 5.2 阶段 A：GPU友好重构（不改变渲染物理逻辑）
1. 类型重构：核心数学从 `double` 切换到 `float`（保留必要边界控制）。
2. 去多态：将几何体/材质/纹理改为 `Type + POD 数据` 的数据导向表示。
3. 扁平化场景数据：
   - `GeometrySoA`：球体、三角形、平面类几何按类型分块存储。
   - `MaterialSoA`：Lambert/Metal/Dielectric/Emissive 统一索引。
   - `TextureTable`：常量色、程序纹理、图像纹理句柄。
4. BVH 扁平化：构建线性节点数组（`left/right` 或 `first/count`），避免递归对象树。
5. 路径积分器改为迭代循环：`for bounce in [0,maxDepth)`，使用显式 `throughput` 与 `radiance` 累计。
6. RNG 改造：每像素独立状态（后续直接对接 CUDA 端 RNG）。

### 5.3 阶段 B：CUDA最小可用后端
1. 构建系统：
   - 引入 CMake，启用 CUDA 语言目标。
   - 分离 `core`（平台无关）与 `backend_cuda` 模块。
2. 内存与上传：
   - CPU 端准备扁平化场景缓冲。
   - 上传到 GPU 全局内存；纹理转为 CUDA texture object。
3. 核心 Kernel：
   - `render_kernel`：每线程负责像素（或样本），执行迭代式路径追踪。
   - `accumulate_kernel`：帧间累积。
   - `tonemap_kernel`：Gamma/映射到显示缓冲。
4. 显示路径（第一版）：
   - GPU 输出 buffer 回传 CPU，再交给现有窗口层显示。
   - 后续可升级为图形互操作以减少拷贝开销。

### 5.4 阶段 C：实时化能力增强
1. 动态相机策略：相机变动时自动清空累积缓冲；静止时持续累积。
2. 降噪接入：优先集成现成时空/离线降噪模块（如 OptiX/OIDN 路线二选一）。
3. 采样优化：NEE（下一事件估计）、重要性采样、俄罗斯轮盘提前终止。
4. 分支优化：按材质/路径状态分桶，降低 warp divergence。

### 5.5 阶段 D：高级优化（按收益择优）
1. Wavefront Path Tracing（多 kernel 队列化）。
2. 压缩 BVH 与访存对齐优化。
3. 体积介质近似与分层质量策略（交互预览低成本、静帧高质量）。

## 6. 关键设计建议
### 6.1 数据结构建议（示意）
1. `struct GpuRay { float3 o,d; float tmin,tmax; };`
2. `struct GpuHit { float t; float3 n,p; int matId; float2 uv; };`
3. `struct GpuBVHNode { float3 bmin,bmax; int leftFirst; int countOrRight; };`
4. `struct GpuMaterial { int type; float3 a,b; int texId; };`
5. `struct RenderParams { int w,h,maxDepth,frameIndex,sppPerFrame; ... };`

### 6.2 随机数建议
1. 使用 `curandStatePhilox4_32_10_t` 或轻量 hash RNG（PCG/XorShift）每像素独立状态。
2. 严禁使用全局共享 RNG 状态。
3. 抖动、镜头采样、BSDF 采样全部走统一 RNG 接口。

### 6.3 正确性对齐策略
1. 固定随机种子与固定采样序，建立 CPU/GPU 可比较输出。
2. 首先比对“低深度、低样本”图像，逐步放开复杂特性。
3. 以 PSNR/SSIM + 关键像素误差双重判定回归。

## 7. 项目计划与排期（建议）
### 7.1 人力建议
1. 渲染算法与核心架构：1 人
2. CUDA 后端与性能调优：1 人
3. 工具链与验证（可兼任）：0.5 人

### 7.2 周期建议（8~12周）
1. W1-W2：阶段 A（数据重构、去递归、RNG 与基准模式）
2. W3-W5：阶段 B（CUDA 最小后端跑通，支持基本材质与几何）
3. W6-W8：阶段 C（实时化增强、降噪接入、交互稳定性）
4. W9-W12：阶段 D（高级优化与质量提升，按收益选择）

## 8. 风险清单与缓解
1. 风险：重构期间正确性回归频繁。  
   缓解：CPU/GPU 双后端长期并存，建立小场景 golden image 测试。
2. 风险：GPU 分支发散严重，性能低于预期。  
   缓解：优先统一材质路径，逐步引入材质分桶与路径队列化。
3. 风险：体积渲染成本过高影响交互。  
   缓解：预览模式降阶（低步长/近似），静帧再启用高质量路径。
4. 风险：构建链路碎片化导致研发效率下降。  
   缓解：统一 CMake 工程与 CI 基准任务，固定编译器与 CUDA 版本。

## 9. 验收标准（建议）
1. 功能验收：核心场景在 GPU 后端正确渲染并可渐进收敛。
2. 性能验收：在目标硬件上达到 M1/M2 的交互目标。
3. 工程验收：支持一键构建、可复现 benchmark、具备回归测试样例。

## 10. 立即执行项（下一步）
1. 建立 `benchmark` 模式：固定分辨率/样本/深度、无窗口持续循环，输出可比较图像与耗时。
2. 完成“去多态 + 扁平化数据”的 CPU 重构分支，确保行为与现有版本一致。
3. 新建 CUDA 工程骨架（CMake + `.cu`），先跑通球体 + Lambertian + BVH 的最小链路。
4. 定义首批回归场景与指标（PSNR、每帧耗时、spp 收敛曲线）。

---

结论：  
当前项目具备较好的路径追踪基础，但要实现 CUDA 实时化，必须先完成数据导向重构与执行模型改造。建议按“重构先行、CUDA落地、实时增强、性能深挖”四阶段推进，预计 8~12 周可形成可交互的 GPU 渐进渲染版本。
